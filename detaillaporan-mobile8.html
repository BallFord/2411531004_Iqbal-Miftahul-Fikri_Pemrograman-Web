HTTP Request dan Integrasi API pada ResepKu

Dokumentasi Praktikum Komunikasi Jaringan REST API, Deserialisasi JSON, FutureBuilder, Operasi CRUD, dan Pengujian Otomatis Menggunakan Framework Flutter

Kembali ke Halaman Report

A. Pendahuluan

Pengembangan aplikasi mobile modern sangat bergantung pada kemampuan pertukaran data secara dinamis dengan layanan web eksternal melalui protokol HTTP dan arsitektur REST API. Pada modul sebelumnya, aplikasi ResepKu masih menggunakan daftar data statis yang tersimpan secara lokal di dalam kode program sehingga cakupan resepnya terbatas dan tidak dapat diperbarui secara real time. Melalui Praktikum Modul 8 ini, arsitektur aplikasi dikembangkan agar mampu berkomunikasi langsung dengan server REST API eksternal menggunakan pustaka http, melakukan serialisasi serta deserialisasi format data JSON ke dalam objek model Dart, dan mengelola pemanggilan asinkron secara terstruktur di dalam kelas layanan khusus.

Selain mengambil daftar resep dari server, integrasi API pada aplikasi mobile juga menuntut pengelolaan siklus hidup state antarmuka yang responsif dan aman dari berbagai skenario kegagalan jaringan. Oleh karena itu, praktikum ini menerapkan widget FutureBuilder untuk menangani tiga kondisi utama, yakni proses memuat data, penanganan galat, serta penyajian data yang dilengkapi fitur pull-to-refresh melalui RefreshIndicator. Lebih lanjut, praktikum ini juga mengimplementasikan operasi manipulasi data secara penuh meliputi penambahan resep baru, pencarian resep berdasarkan kata kunci, pembaruan nama resep, penghapusan data, hingga pengujian unit otomatis tanpa koneksi internet menggunakan MockClient.

B. Tujuan

Tujuan dari praktikum ini adalah:

  • Memahami konsep komunikasi jaringan berbasis protokol HTTP dan integrasi layanan REST API menggunakan format pertukaran data JSON pada framework Flutter.
  • Mengimplementasikan lapisan layanan jaringan dan model deserialisasi untuk memisahkan logika komunikasi server dari lapisan antarmuka pengguna.
  • Mengelola operasi asinkron menggunakan widget FutureBuilder untuk menangani seluruh siklus tampilan data meliputi kondisi memuat, berhasil memuat data, dan penanganan kesalahan jaringan beserta mekanisme muat ulang.
  • Menerapkan operasi CRUD serta pencarian data secara dinamis menggunakan metode HTTP GET, POST, PUT, dan DELETE dengan pemeriksaan siklus hidup widget.
  • Melakukan pengujian unit otomatis terhadap logika pemrosesan JSON dan pemanggilan layanan HTTP tanpa ketergantungan koneksi internet menggunakan MockClient.

Bagian B — RecipeService dan FutureBuilder

5. Langkah B.1 — Membuat RecipeService

Semua komunikasi dengan server diletakkan di satu class. Widget tidak memanggil http secara langsung. Buat folder lib/services, lalu buat file recipe_service.dart.

Kode ini berfungsi memusatkan seluruh komunikasi jaringan aplikasi ResepKu dengan REST API dummyjson.com agar komponen antarmuka tidak memanggil package http secara langsung. Di dalamnya terdapat method fetchRecipes yang mengirimkan permintaan HTTP GET ke endpoint /recipes?limit=50 dengan batas waktu tunggu selama 10 detik, memeriksa kode status respons menggunakan _checkStatus agar status gagal di luar rentang 2xx melemparkan RecipeServiceException, serta menguraikan data JSON pada key recipes menjadi daftar objek List<Recipe> melalui Recipe.fromJson.

6. Langkah B.2 — Mendaftarkan RecipeService sebagai Provider

Ganti seluruh isi lib/main.dart. RecipeService didaftarkan dengan Provider biasa (bukan ChangeNotifierProvider) karena service tidak menyimpan state yang berubah. ThemeProvider dari Latihan 1 Modul 6 juga tetap didaftarkan.

Pembaruan pada file lib/main.dart ini mendaftarkan RecipeService ke dalam daftar providers milik MultiProvider menggunakan Provider biasa karena kelas layanan tersebut tidak menyimpan state yang berubah maupun memerlukan pemanggilan notifyListeners(). Selain menginisialisasi RecipeService melalui parameter create, disertakan parameter dispose yang memanggil service.close() untuk menutup koneksi http.Client secara bersih ketika aplikasi dihentikan.

7. Langkah B.3 — Widget ErrorView

Buat widget untuk error state agar dapat dipakai di beberapa halaman.

Widget ErrorView merupakan komponen reusable (StatelessWidget) yang dirancang untuk menampilkan kondisi kegagalan secara seragam di berbagai halaman aplikasi. Widget ini menyusun ikon jaringan terputus, teks keterangan kesalahan, serta tombol aksi FilledButton.icon berlabel "Coba lagi" di tengah layar, di mana menekan tombol tersebut akan menjalankan fungsi callback onRetry yang diteruskan dari halaman pemanggil untuk mengulang permintaan data.

Sementara itu, deretan ChoiceChip untuk filter kategori cuisine kini diambil langsung dari daftar recipes yang diterima dari server.

Pertanyaan Analisis

16. Pada skenario 2, setiap refresh membuat objek Recipe yang baru dari JSON. Mengapa status favorit tetap benar? Hubungkan dengan cara FavoriteProvider membandingkan resep (Modul 6).

Status favorit tetap bertahan dengan benar karena FavoriteProvider melacak dan membandingkan resep berdasarkan nilai id unik milik resep. Meskipun proses pull-to-refresh mengurai ulang respons JSON dan menghasilkan objek Recipe baru di memori, setiap objek tersebut tetap membawa nilai id yang identik dengan data sebelumnya dari server, sehingga pemeriksaan status favorit pada FavoriteProvider tetap cocok dan ikon hati maupun angka badge tidak berubah.

17. Pada skenario 3, mengapa menekan tombol grid tidak memunculkan indikator loading? Apa yang akan terjadi jika future ditulis langsung di dalam build()?

Menekan tombol grid tidak memunculkan indikator loading karena objek _recipesFuture diinisialisasi hanya satu kali di dalam initState(), sehingga pemanggilan setState() saat mengubah tata letak grid/list hanya membangun ulang tampilan menggunakan Future yang statusnya sudah selesai. Apabila pemanggilan fetchRecipes() diletakkan langsung di dalam metode build(), setiap perubahan state antarmuka, seperti mengganti tampilan grid, memilih filter kategori, atau menekan tombol favorit, akan menciptakan Future baru yang memicu permintaan HTTP ulang ke server dan terus-menerus menampilkan indikator loading.

18. HomePage tidak memanggil http.get secara langsung, melainkan melalui RecipeService. Sebutkan dua keuntungan cara ini!

Pemisahan komunikasi jaringan ke dalam kelas RecipeService memberikan dua keuntungan utama, yaitu pemisahan tanggung jawab dan penggunaan ulang kode, karena konfigurasi URL, timeout, parsing JSON, serta validasi status HTTP terpusat di satu tempat sehingga kode UI pada HomePage tetap bersih dan logika API mudah dipakai ulang oleh halaman lain. Keuntungan kedua adalah kemudahan pengujian, sebab RecipeService dirancang menerima injeksi http.Client opsional yang memungkinkan logika pengambilan data diuji secara mandiri menggunakan mock client tanpa harus merender tampilan widget maupun bergantung pada koneksi internet.

19. Setelah POST berhasil, server memberi id baru, tetapi resep tidak muncul saat daftar dimuat ulang. Jelaskan penyebabnya, dan bagaimana aplikasi dengan server sungguhan biasanya menampilkan data yang baru ditambahkan!

Resep baru tidak muncul saat daftar dimuat ulang karena dummyjson.com merupakan layanan API tiruan yang hanya menyimulasikan respons keberhasilan POST /recipes/add beserta pembuatan ID sementara tanpa benar-benar menyimpan data tersebut ke dalam basis datanya, sehingga permintaan GET /recipes berikutnya tetap mengembalikan daftar awal. Pada aplikasi yang terhubung ke server sungguhan dengan basis data permanen, data yang baru ditambahkan umumnya ditampilkan dengan cara memuat ulang daftar dari server setelah menerima data kembalian dari Navigator.push, atau menyisipkan langsung objek resep baru hasil respons POST ke dalam list di state lokal agar langsung tampil tanpa harus mengunduh ulang seluruh data.

20. Di AddRecipePage terdapat if (!mounted) return; setelah await. Jelaskan skenario yang dicegah oleh baris tersebut!

Baris if (!mounted) return; mencegah terjadinya runtime error apabila pengguna menutup halaman AddRecipePage saat proses pengiriman data await service.addRecipe(...) masih berlangsung di latar belakang. Jika operasi await selesai ketika widget halaman tersebut sudah dihancurkan dari widget tree, pemanggilan Navigator.pop(), setState(), atau ScaffoldMessenger.of(context) pada BuildContext yang sudah tidak aktif akan menyebabkan aplikasi crash, sehingga pengecekan !mounted memastikan eksekusi kode segera dihentikan dengan aman.

D. Kesimpulan

Berdasarkan seluruh rangkaian praktikum pada Modul 8, aplikasi ResepKu telah berhasil bertransformasi dari aplikasi berbasis data statis menjadi aplikasi dinamis yang terintegrasi penuh dengan layanan REST API eksternal melalui kelas RecipeService. Pemisahan tanggung jawab antara lapisan akses jaringan, pemetaan model data, serta tampilan antarmuka berbasis FutureBuilder terbukti menghasilkan arsitektur kode yang bersih, terstruktur, dan tangguh dalam menangani berbagai kondisi jaringan, mulai dari jeda pemuatan data, kegagalan koneksi, pembaruan data melalui RefreshIndicator, hingga keamanan siklus hidup widget menggunakan pemeriksaan mounted setelah setiap proses await.

Selain itu, implementasi fitur CRUD lengkap, yang mencakup pengambilan daftar resep, pencarian berdasarkan kata kunci, penambahan resep baru, pembaruan nama resep, serta penghapusan data, berhasil dijalankan dan diverifikasi melalui berbagai skenario pengujian antarmuka. Keandalan kode di balik layar juga telah divalidasi melalui pengujian unit otomatis menggunakan MockClient pada berkas test/recipe_service_test.dart, yang memastikan logika konversi data JSON dan penanganan status galat HTTP berjalan akurat tanpa bergantung pada ketersediaan jaringan internet.
